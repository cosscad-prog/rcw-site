# 접수 엔드포인트 시험 (배포 없이)

`api/contact.js` · `api/trial.js` 를 **실제 파일 그대로** 불러 `fetch` 만 가짜로 바꿔 돌린다.
Supabase 와 텔레그램에는 아무것도 나가지 않고, 설치할 것도 없다.

```bash
node docs/_tests/contact-api.test.js
node docs/_tests/trial-api.test.js
node docs/_tests/todo-names.test.js
node docs/_tests/todo-sync.test.js
node docs/_tests/todo-render.test.js
node docs/_tests/todo-history.test.js
```

각 줄의 `HTTP … supabase=n telegram=n` 과 `▶ … OK` 를 눈으로 확인한다.
`실패` 가 하나라도 있으면 고치기 전에 배포하지 말 것.

## 보는 것

| 확인 | 왜 |
|---|---|
| 정상 접수 → 200 · 저장 1회 · 알림 1회 | 기본 경로 |
| honeypot 채워짐 → 200인데 **저장·알림 0회** | 봇에게 실패를 알려주면 형식을 바꿔 다시 온다 |
| 필수 누락·이메일 형식 오류 → 400 | DB 의 not null 위반이 500 으로 새지 않게 |
| Supabase 실패 → 500 · **알림 0회** | 저장 안 됐는데 알림만 가면 안 된다 |
| 텔레그램 실패 → **접수는 200** | 알림은 부가 기능이다 |
| 한도 초과 본문 → 저장 ≤ DB 제약, 알림 ≤ 4096자 | 텔레그램 상한을 넘으면 알림이 통째로 사라진다 |
| (trial) 보낸 id == 저장 id == 응답 id | 다운로드 클릭을 신청과 엮는 열쇠다 |

## ⚠️ 스텁을 고칠 때

가짜 응답은 **실제 상태코드를 그대로 모사해야 한다.** Supabase 는 `Prefer: return=minimal`
INSERT 에 **201 + 빈 본문**(PATCH 는 204)을 준다. 전에 스텁이 INSERT 를 204 로 흉내내
"행은 저장됐는데 500" 이라는 실패를 테스트가 못 잡았다. 상세 `docs/CUSTOMER_PORTAL.md`.

## 화면 쪽 확인

폼(`contact.html` / `trial.html`)은 헤드리스 크롬으로 확인한다 — `window.fetch` 만 가짜로
끼우고 제출까지 몰아본 뒤 성공/오류 안내가 실제로 뜨는지 본다. 방법은 이 저장소 밖의
작업 메모(`site-verify-headless`)에 있고, 요지는 **실행마다 프로필을 새로 만들 것**과
**생성한 파일을 grep 해 역슬래시가 깨지지 않았는지 확인할 것** 두 가지다.

## 할 일 동기화 (`todo-sync.test.js`)

`todo.html` 안의 Supabase 동기화 블록을 **그 파일에서 떼어 내** 돌린다(사본이 아니다).
서버·표 없이 확인한다.

| 확인 | 왜 |
|---|---|
| 세션 없으면 서버를 부르지 않고 로그인 화면 | 로그인 전에 남의 이름으로 읽으려 들면 401 만 쌓인다 |
| 로그인 뒤 서버에 줄이 없으면 지금 로컬 것을 올림 | 첫 기기의 목록이 빈 목록에 덮이면 안 된다 |
| 저장 실패 → 배지가 **빨강 유지**, 밀린 저장 안 잊음 | 저장 안 된 것을 초록으로 덮으면 그대로 날린다 |
| 다른 기기 변경은 화면 복귀 때 가져옴 | 실시간 구독 대신 `visibilitychange` 로 본다 |
| 서버 `updated_at` 이 그대로면 다시 그리지 않음 | 편집 중에 화면이 튀지 않게 |
| **안 올라간 내 변경이 있으면 pull 하지 않고 push** | 순서가 바뀌면 방금 쓴 것이 사라진다 |
| 만료 토큰은 저장 전에 미리 refresh | 만료된 채 쏘면 401 로 조용히 안 저장된다 |
| 표가 없으면 **"표가 없습니다 — supabase-todo.sql 실행"** | "동기화 실패" 한 마디로는 어디를 고칠지 알 수 없다 |

## ⚠️ 못 잡는 것

RLS 정책은 여기서 확인되지 않는다 — `docs/supabase-todo.sql` 을 실제로 돌렸는지,
`with check` 가 들어갔는지는 로그인해서 한 번 써 보고 Supabase 표에 줄이 생기는지로만 안다.

## 할 일 화면 (`todo-render.test.js`)

`todo.html` 의 컬럼 빌더 두 개를 상태 10가지로 그려 본다. **보는 것은 하나 — 예외가 나나.**

`render()` 는 맨 처음에 `list.innerHTML=""` 를 한다. 그 뒤에서 예외가 하나만 나도 화면이
"일부만 이상"이 아니라 **통째로 빈다.** 2026-09-01 에 실제로 그랬다 —
`buildImportantNormalColumn` 이 `buildColumn` 의 지역변수 `hidSub` 를 읽어서,
**오른쪽 상단 패널이 빌 때마다** `ReferenceError`. 항목을 숨기니 그 순간 판이 사라졌다.

## ⚠️ 못 잡는 것

`row()` · `makeDropZone()` · `updateBoardHeight()` 는 스텁이라 안 지난다. 그쪽에서 나는
예외는 이 검사로 안 잡힌다 — 브라우저에서 항목을 실제로 하나 끌어 보는 것으로만 안다.
`정상` 상태만 돌려 보면 이 버그도 통과한다(그래서 상태를 10가지 둔다).

## 할 일 3단계 저장 (`todo-history.test.js`)

| 단계 | 표 | 무엇 | 언제 |
|---|---|---|---|
| 1 | `todo_state` | 지금 목록 | 고칠 때마다 |
| 2 | `todo_day` | 하루에 한 줄 = **그날의 마지막 상태**, 30일치 | 1단계 저장이 성공한 뒤, 1분에 한 번 |
| 3 | `todo_archive` | 30일 지난 하루치를 **한 줄에** | 하루 한 번, 페이지를 열 때 |

**제일 중요한 것은 `hxFold` 의 순서다 — 보관에 넣기 전에 지우면 그 날은 없어진다.**
검사에서 순서를 뒤집으면 4개가 FAIL 난다(헛돌지 않는 것을 확인함).

| 확인 | 왜 |
|---|---|
| 넣기가 **지우기보다 먼저** | 반대로 하면 중간에 끊길 때 그 날이 통째로 사라진다 |
| 보관 쓰기 실패 → **하루치를 안 지움**, 다음에 재시도 | 위와 같은 이유 |
| 같은 날짜가 두 번 안 들어감 | 지우기가 끊겨 다시 넣게 되는 경우 |
| 하루에 한 번만 정리 | 열 때마다 30일치를 훑지 않게 |
| 1분 안에는 하루치를 다시 안 씀, 그래도 안 잊음 | 타자마다 서버를 두드리지 않게 |
| 되돌리기 → **직전 상태가 보관에 남음** | 되돌린 것이 틀렸을 때 다시 돌아올 곳 |

## ⚠️ 못 잡는 것

- 자정을 넘길 때 날짜가 바뀌는 것 — 검사는 항상 "오늘" 안에서만 돈다.
- RLS 정책. 세 표 모두 `docs/supabase-todo.sql` 을 실제로 돌려야 산다.
- 보관 한 줄이 몇 년 뒤 얼마나 커지는가. 하루치 한 개가 대략 몇 KB 라
  1년이면 몇 MB 수준이지만, 실제 크기는 화면 하단 "보관 N일" 로만 알 수 있다.

## 할 일 — 없어진 이름 (`todo-names.test.js`)

**부르는데 어디에도 선언이 없는 이름**을 찾는다. 한 가지만 본다.

2026-09-01 에 백업 절을 통째로 지웠는데, 그 절 **끝에 얹혀 있던 `seed()` 와 `mk()`** 가
같이 날아갔다. `mk()` 는 `add()` 가 부르는 것이라 **[추가] 버튼이 아무 일도 안 하게** 됐다.
그런데 **문법 검사도, 다른 검사 네 개도 전부 통과했다** — `ReferenceError` 는 그 줄을
지나야만 나기 때문이다. 화면은 멀쩡해 보였다(저장된 HTML 이라 옛 판이 그대로 박혀 있다).

절을 지울 때는 **그 절에 원래 속하지 않은 함수가 딸려 나갔는지** 이것으로 확인한다.

## ⚠️ 못 잡는 것

정규식이지 파서가 아니다. **스코프를 안 본다** — "어느 함수 안에 선언됐나"는 못 가린다.
그건 `todo-render.test.js` 가 실제로 그려 보며 잡는다(`hidSub` 가 그 경우였다).
여기서 잡는 것은 **아예 아무 데도 없는 이름** 하나뿐이다.

### 진짜로 눌러 보는 확인 (크롬 필요)

검사 다섯 개가 다 통과해도 페이지가 죽어 있을 수 있다. 위가 정확히 그 경우였다.
`todo.html` 사본의 `<head>` 에 `window.onerror` 수집기를, `</body>` 앞에 프로브를 끼우고
헤드리스 크롬 `--dump-dom` 으로 한 번 돌리면 **init 중 예외 / [추가] 를 눌렀을 때 항목 수가
느는지**까지 보인다. 타이머가 필요 없게 프로브를 **동기로** 짜는 것이 요령이다
(`--virtual-time-budget` 을 쓰면 매달린다). 두 판을 본다 — **빈 브라우저**와
**localStorage 에 목록이 이미 있는 브라우저**. 위 사고는 앞의 판에서만 다르게 터졌다.

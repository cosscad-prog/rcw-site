# 제품 문의 답변 메일 (2026-09-07)

홈페이지 문의(`/contact` → 텔레그램 · `beimptech+rcw@gmail.com` · `/admin` [문의] 탭)에
**답장할 때 쓰는 표준 문안**이다. 문의는 대부분 같은 두 가지를 묻는다 —
**"우리 업무에는 어떤 버전이 맞나"** 와 **"얼마인가"**.

문안은 **HTML 세 통**이다. 브라우저로 열어 고치고, 단추 하나로 메일에 붙여넣는다.

| 파일 | 언제 |
|---|---|
| [`mail/reply-1-stick-core.html`](mail/reply-1-stick-core.html) | 평면 **스틱(Stick)** 타입뿐일 때 → **Core** |
| [`mail/reply-2-unit-standard.html`](mail/reply-2-unit-standard.html) | **유닛(Unit) 타입 · 삼각형 등 평면이 아닌 유닛** → **Standard** |
| [`mail/reply-3-curved-professional.html`](mail/reply-3-curved-professional.html) | **곡선(커브) · 판재(Sheet)** → **Professional** |

## 보내는 방법 — **HTML 파일을 첨부한다** (2026-09-08 결정)

본문에 붙여넣지 않고 **파일로 첨부**한다. 한꺼번에 돌리지 않고 **한 건씩 검토해서** 보낸다.

```bash
node "docs/mail/export-attach.js" "docs/mail/<그 고객 편지>.html" --title "RCW V5 안내"
```

⚠️ **작업용 파일을 그대로 첨부하면 안 된다.** 위쪽 도구 막대와 안내 상자에는
"가격 두 칸이 아직 비어 있습니다" 같은 **우리끼리 보는 메모**가 들어 있고,
받는 분이 파일을 열면 그것부터 읽는다. 위 명령이 그 부분(도구 막대 · 안내 상자 ·
제목 칸 · 스크립트 · 안 쓰는 CSS)을 떼고 `첨부_<이름>.html` 을 만든다.

- **《 》 가 하나라도 남아 있으면 만들지 않고 멈춘다.** 채운 뒤 다시 돌리거나, 일부러면 `--force`
- 떼어 낸 뒤 **편지 본문 글자 수가 그대로인지** 스스로 확인하고 알려 준다
- 만든 파일은 **한 번 열어 보고** 첨부한다

작업용 파일 위쪽의 도구 막대는 **메일에 안 들어간다**(첨부본에는 아예 없다).

- **편집 켜기** — 화면에서 바로 고친다. ⚠️ **저장되지 않는다.** 다음에도 쓸 문구는 HTML 파일을 직접 고칠 것
- **빈 칸 표시 끄기** — 노란 표시를 지우고 *실제로 보내지는 모습*을 확인
- **제목 복사** / **메일용으로 복사** — 서식 그대로 복사된다(노란 표시는 자동으로 빠진다).
  브라우저가 복사를 막으면 **선택만 해 두고 Ctrl+C 를 누르라고 안내**한다
- 페이지를 열면 오른쪽에 **"채울 곳 N군데"** 가 뜬다

검사: `node docs/_tests/mail-pages.test.js` (헤드리스 크롬)

## ★ 먼저 — **이 프로그램의 대상 고객인가**

형상을 따지기 전에 이것이 먼저다. RCW 는 **실제 발주자 · 제작자를 위한 도구**다.
3D 모델링은 **물량 산출과 가공도를 위해 정확한 모델을 만드는 수단**이지, 보여주기 위한 것이 아니다.

⚠️ **컨설팅 회사는 대상 고객이 아니다.** 그들은 검토만 하고, 머릿속에 안 그려지거나
의심스러운 부분만 3D 로 세워 본다. 발주도 가공도 하지 않으므로 이 프로그램의 값어치가
닿지 않는다. **그런 문의에는 권하지 않는 편지를 보낸다** — 팔고 나서 "쓸 데가 없더라" 가
되는 것이 서로에게 나쁘다.

아래 형상 기준은 **대상 고객으로 판단된 뒤**에 쓰는 것이다.

## ★ 어느 문안을 보낼지는 **형상**이 정한다

기능 목록이 아니라 이것이 먼저다. 형상이 감당되지 않으면 뒤의 기능은 쓸 일이 없다.

| 프로젝트 형상 | 필요한 버전 |
|---|---|
| 평면 **스틱(Stick)** 타입 | **Core** |
| **유닛(Unit) 타입** · **삼각형** 등 평면이 아닌 유닛 | **Standard** |
| **곡선(커브)**이 있는 형상 · **판재(Sheet)** 가공 | **Professional** |

- Core 는 **폴리라인 형상 · 유리 · 창호(Vent) · 그릴(Grill) · 판재(Sheet Panel)** 에 제한이 있다.
  **단순한 스틱 타입까지**가 적정 범위다.
- 같은 유닛 타입이라도 **평면 유닛이냐 아니냐**에서 갈린다. 삼각형 유닛이 하나라도 들어오면 Standard.
- **곡선은 Standard 로 대신할 수 없다.** 형상을 세우는 첫 단계에서 막히므로 Professional 이 필수다.

### ⚠️ 컨설팅 문의는 기본이 ②번(Standard 이상)이다

**컨설팅이 필요할 만큼의 프로젝트는 단순 스틱인 경우가 드물다.** 유닛 타입이거나
비정형이 섞여 있고, 바로 그 지점에서 Core 는 한계가 온다. 컨설팅이라는 말만 보고
"검토용이니 Core 로 충분하겠지" 로 가면 **도입 직후에 막힌다.**

형상을 모르겠으면 **짐작해서 권하지 말고**, ②번 문안의 형상 표를 그대로 두고
"어느 쪽에 해당하시는지 알려 주시면" 한 줄로 물어보는 편이 낫다.
가장 확실한 것은 **형상 자료 하나를 받는 것**이다.

## ⚠️ 보내기 전에

1. **가격 칸을 채웠는가.** 빈 칸 그대로 나가면 안 된다. **VAT 별도/포함**도 함께.
2. **노란 《 》 자리를 전부 고쳤는가.** [빈 칸 표시 끄기] 로 눈으로 확인한다.
3. **없는 기능을 있다고 하지 말 것.** 표에 없는 것을 물으시면 "지금은 없습니다" 가 맞는 답이다.
   돌려 말하면 도입 후에 반드시 문제가 된다.
4. 버전 번호 뒤에 **조사를 바로 붙이지 말 것**(끝자리 발음에 따라 갈린다 — `5.3.0 을`).
5. 답장은 **받은 알림 메일에 그대로 회신**하면 문의자에게 간다(`Reply-To` 가 문의자다).

## 채워 넣는 곳

| 자리 | 무엇 |
|---|---|
| `《회사명》 《담당자님》` | 문의 폼에 적혀 온 그대로 |
| `《업무》` | "커튼월 컨설팅 업무" 처럼 문의자의 말을 그대로 |
| **Core · Standard 가격** | **반드시 채운다.** ③번(Professional)은 **검토 뒤에** 제안하는 것이 원칙이라 비워 둔다 |
| 여러 대 · 업그레이드 조건 | 정책이 정해지면 세 파일에 고정 문구로 박아 둔다 |
| `《도입 초기에 …》` | 지원 범위를 약속할 수 있을 때만 남기고, 아니면 지운다 |
| `《30분 정도》` · `《보통 영업일 3~5일》` | 시연 시간 · 검토 기간 |
| `《보내는 사람》` | 이름 |

## 왜 이 순서인가

**감사 → 무엇인지 → 형상 기준 → 어느 버전 → 미리 아셔야 할 점 → 가격 → 먼저 써 보기 → 다음 단계.**

- 가격을 먼저 적으면 그 숫자 하나로 판단이 끝난다. **무엇을 사는 것인지 먼저** 말한다.
- **단점을 우리 입으로 먼저 말한 다음** 가격을 적는다. 도입 후에 "듣던 것과 다르다" 가
  나오지 않는 것이 계약 한 건보다 낫다. (Rhino 별도 필요 · 초기 단면 등록 작업 · PC 1대 기준)
- 평가판을 가격 **뒤에** 두는 것도 같은 이유다 — 숫자를 보고 망설이는 자리에서
  "직접 확인해 보십시오" 가 바로 이어져야 한다.
- ③번만 순서가 다르다. **가격 대신 진행 방법**이 온다 — 곡선은 형상마다 필요한 것이 달라,
  보지 않고 적은 숫자는 반드시 틀린다.

## 기능 설명의 출처

세 문안의 기능 서술은 홈페이지 **버전 비교 표**(`index.html`)와 빌드 설정에서 확인한 것만 적었다.
표가 바뀌면 이 문안도 같이 고쳐야 한다. Core 에서 실제로 빠지는 것은 창호 · 그릴 ·
유닛 리스트/표 · BIM 데이터 · 웹뷰어 · 사용자 바리스트 · 유닛 타입 모델링이다.
